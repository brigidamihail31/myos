# 01. Границы ОС и нефункциональные требования

## 1. Название и концепция операционной системы

**MyOS** — учебная операционная система с монолитным ядром, реализуемая
на Python 3.10+ с использованием SQLite в качестве единого хранилища
для файловой системы, реестра процессов, журнала системных вызовов и
данных пользователей.

Основная идея проекта — продемонстрировать базовые принципы построения
ОС (ядро, системные вызовы, пространство пользователя, разграничение
прав) без работы с реальным аппаратным обеспечением. Всё «железо»
имитируется заглушками, что позволяет сосредоточиться на логике
взаимодействия модулей и проектировании API ядра.

**Ключевые понятия:** ядро, пространство ядра (kernel space),
пространство пользователя (user space), системный вызов, процесс,
поток, дескриптор, планировщик, виртуальная память, хэширование.

## 2. Границы системы

### 2.1. Что входит в границы ОС

| Подсистема | Что реализуется |
|---|---|
| Управление процессами | Создание, состояния, завершение, лимит на количество процессов |
| Управление памятью | Учёт выделенной памяти по процессам, страничная модель |
| Файловая система | Создание, чтение, удаление файлов поверх таблицы `files` в SQLite |
| Подсистема безопасности | Аутентификация (SHA-256), авторизация по ролям `admin` / `user` |
| Командная оболочка | Цикл ввода команд, приглашение `user@studyos:~$`, базовые команды |
| Журналирование | Запись всех системных вызовов в таблицу `syscalls_log` |

### 2.2. Что НЕ входит в границы ОС (и почему)

| Исключено | Обоснование |
|---|---|
| Реальные драйверы устройств | Требуют знания аппаратной части; заменены заглушками (таймер, клавиатура, диск, экран) |
| Обработка аппаратных прерываний | Невозможно реализовать на Python без прямой работы с железом |
| Сетевые протоколы | Вне темы проекта, требует отдельной подсистемы |
| Графический интерфейс | Не является темой; достаточно командной оболочки |
| Внешние службы каталогов (LDAP и т. п.) | Избыточны для учебной ОС за отведённое время |
| Реальная работа с секторами диска | SQLite выступает физическим носителем, детали диска абстрагированы |
| Многопоточная синхронизация на уровне ОС | Имитируется последовательным планировщиком |

> Честно очерченные границы — признак профессионализма, а не слабости:
> они позволяют сосредоточиться на действительно важных аспектах.

## 3. Сценарии использования

Роли: **обычный пользователь** (`user`), **администратор** (`admin`),
**система** (фоновые процессы — планировщик, сборщик мусора).

### 3.1. Вход в систему
- **Действующее лицо:** пользователь.
- **Последовательность вызовов:** `sys_login(login, password)` → ядро
  → подсистема `auth` → таблица `users` (сравнение SHA-256) → запись
  в `syscalls_log`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `auth.py`, `db.py`.

### 3.2. Создание файла
- **Действующее лицо:** авторизованный пользователь.
- **Вызовы:** `sys_create_file(path, content)` → проверка прав →
  `fs.create_file` → таблица `files` → лог в `syscalls_log`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `fs.py`, `db.py`.

### 3.3. Чтение файла
- **Вызовы:** `sys_read_file(path)` → `fs.read_file` → проверка
  доступа (`auth.authorize_file_access`) → таблица `files`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `fs.py`, `auth.py`, `db.py`.

### 3.4. Просмотр списка файлов
- **Вызовы:** `sys_list_files()` → `fs.list_files` → фильтрация
  по владельцу для обычного пользователя.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `fs.py`, `db.py`.

### 3.5. Запуск процесса
- **Вызовы:** `sys_exec(name, memory)` → `scheduler.create_process` →
  проверка лимита → таблица `processes`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `scheduler.py`, `db.py`.

### 3.6. Просмотр списка процессов
- **Вызовы:** `sys_ps()` → `scheduler.list_processes` → таблица `processes`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `scheduler.py`, `db.py`.

### 3.7. Завершение процесса
- **Вызовы:** `sys_kill(pid)` → `scheduler.kill_process` → удаление
  записи из `processes`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `scheduler.py`, `db.py`.

### 3.8. Просмотр журнала системных вызовов
- **Вызовы:** `sys_logs(limit)` → таблица `syscalls_log`.
- **Модули:** `shell.py`, `syscalls.py`, `db.py`.

### 3.9. Выделение памяти процессу
- **Вызовы:** `sys_mem_alloc(pid, size)` → `memory.alloc` → обновление
  поля `memory` в `processes`.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `memory.py`, `db.py`.

### 3.10. Завершение работы ОС
- **Вызовы:** `sys_shutdown()` → запись в лог → выход из оболочки.
- **Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`.

## 4. Нефункциональные требования

| Категория | Требование | Метрика / способ проверки |
|---|---|---|
| **Производительность** | Время обработки одного системного вызова ≤ 50 мс | `time.perf_counter` внутри `_timed()` |
| **Производительность** | Не менее 10 одновременных процессов | `MAX_PROCESSES = 10` в `config.py` |
| **Производительность** | Запуск оболочки ≤ 1 с | `python -m src.shell` в терминале |
| **Надёжность** | Ядро не падает при ошибке пользовательского процесса | `try/except` в `_timed()` + `shell.main()` |
| **Надёжность** | Ошибка процесса пишется в журнал | статус `ERROR: ...` в `syscalls_log` |
| **Надёжность** | Превышение лимита процессов → исключение, а не падение | `RuntimeError` в `scheduler.create_process` |
| **Безопасность** | Все пароли только в виде SHA-256 | таблица `users`, поле `password_hash` |
| **Безопасность** | Обычный пользователь видит только свои файлы | фильтр в `sys_list_files` |
| **Безопасность** | Все системные вызовы логируются | таблица `syscalls_log` |
| **Поддерживаемость** | Размер модуля ≤ 300 строк | `wc -l src/*.py` |
| **Поддерживаемость** | Каждый модуль решает одну задачу | структура `src/` (см. `02_OS_Architecture.md`) |
| **Ресурсоёмкость** | Только Python 3.10+ и stdlib | без внешних зависимостей |
| **Ресурсоёмкость** | Размер БД для типового набора данных ≤ 10 МБ | `ls -lh db/os.sqlite` |

## 5. Анализ рисков

| № | Риск | Стратегия минимизации |
|---|---|---|
| 1 | **Нехватка времени** на реализацию всего запланированного | Приоритизация: ядро → БД → файловая система → оболочка → дополнительные функции |
| 2 | **Блокировки SQLite** при частых обращениях | Единое соединение (`_connection`) + `check_same_thread=False` + контекстный менеджер `cursor()` |
| 3 | **Сложность отладки системных вызовов** | Сквозное логирование: каждый вызов фиксируется в `syscalls_log` с аргументами и статусом |
| 4 | **Забытая обработка ошибок** | Единая обёртка `_timed()` + `try/except` в главном цикле shell; чек-лист по модулям |
| 5 | **Потеря целостной картины проекта** | Подробная документация в `docs/`, регулярная сверка с ней |
| 6 | **Изменение схемы БД** ломает ранее написанный код | Все операции с БД сосредоточены в `db.py`; остальные модули работают только через его функции |
| 7 | **Случайная потеря файла БД** | `db/os.sqlite` в `.gitignore`; инициализация выполняется командой `python src/db.py` |

## 6. Описание созданного прототипа

**Реализованные модули:**

| Модуль | Назначение |
|---|---|
| `src/config.py` | Пути, лимиты, константы |
| `src/db.py` | Соединение с SQLite, инициализация 4 таблиц, `hash_password`, CRUD |
| `src/syscalls.py` | `log_syscall`, 13 системных вызовов, блок самопроверки |
| `src/kernel.py` | Загрузка ядра, проксирующие методы подсистем |
| `src/scheduler.py` | Создание, состояния, планирование, завершение процессов |
| `src/memory.py` | Выделение и освобождение памяти процессам |
| `src/fs.py` | Создание, чтение, удаление и список файлов |
| `src/auth.py` | Аутентификация (SHA-256) и авторизация по ролям |
| `src/shell.py` | Командная оболочка с приглашением `user@studyos:~$` |

**Как проверить:**

```bash
# 1. Инициализация БД (создаст db/os.sqlite)
python src/db.py

# 2. Самопроверка системных вызовов
python -m src.syscalls

# 3. Запуск оболочки
python -m src.shell
